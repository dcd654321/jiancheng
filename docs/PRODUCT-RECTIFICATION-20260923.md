# 渐成习惯打卡：产品审阅整改方案

日期：2026-09-23。状态：待实施的整改文档，不代表代码已完成、正式云已验收或小程序可上线。

## 1. 依据、目标与边界

主要依据为本机 `docs/PRODUCT-OPTIMIZATION-20260923.md` 的第 3 节界面审阅及第 10、12、13 节优先级、验收和证据边界；同时对照当前 `miniprogram/` 页面源码及已完成的 `docs/UX-FIX-20260920.md`，避免把旧版已修问题重新列为待办。原报告的五张 363×785 模拟器截图保存在本机 `docs/audits/2026-09-23-product-optimization/`，但报告及截图目前未纳入 Git；本文独立列出问题与验收口径，不把未入库截图当作远端可复核附件。

整改目标：新用户能看懂并完成一次小动作；老用户在忙和漏做后仍愿意回来；所有反馈使用真实记录，不靠虚构连续天数、积分或“AI”包装。面向普通用户，保留“今日／进度／我的”三 Tab，不扩成待办、课程或社群产品。

本轮**只形成实施方案，不修改业务代码、云函数、数据库或平台设置**。后续新增流程、数据字段、消息提醒和分享能力，实施前分别建立 OpenSpec 变更；继续只在 `dev` 开发，用户真机验收且明确要求后才考虑合并 `main`。正式云身份、集合权限和双账户验证仍是公开使用的独立前置门槛，界面整改不能代替它。

## 3. 实施顺序（按在职个人开发者控制规模）

### P0-A：先让人看懂并完成一次

范围限 R01、R02 及对应的 R08。先改创建页和今日任务卡，不增加数据库字段、云函数、后台任务或新 Tab。复用现有 `minimum` 数值字段与同单位规则：例如“读 20 分钟／忙时读 2 分钟”。报告中的“读 20 分钟／忙时读 2 页”跨单位示例**当前模型不支持**，不得仅换文案假装已支持；若用户测试证明跨单位确有价值，另开数据模型变更。忙时目标不能大于或等于平时目标；目标为 1 时不提供无效的降档。

今日卡的“今天做小一点”仍表示**先选较小目标，再由用户确认实际完成**；不能把点击降档当作自动打卡。已有用户未设置忙时目标时保持可选设置入口，不自动替他修改计划。创建后如果用户明确选择明天开始，不展示“今天可完成”的假入口。

预估为 2—3 个开发晚上加 1 次非开发者走查；先只处理这条闭环，不同时改统计、分享或提醒。

### P0-B：漏做后轻松回来

只新增从现有计划和记录推导的状态，不新增权威存储字段或自动补写。判断以用户所在日期的**已结束计划日**为单位；跨日、休息日、暂停／归档、计划次日生效、离线待同步与多设备冲突都要有测试。离线未确认记录存在时，不用“你没做”否定用户已在本机记录的行动，应显示待同步状态。完成后的鼓励反馈不阻塞下一操作。

预估 2—3 个开发晚上。若需要改变现有领域规则或数据结构，先停在设计复核，不在页面层硬编码例外。

### P0-调研：提醒可行性闸门

计划时间目前仅排序。先核对微信当前可用的消息模板、用户主动授权条件、可发送次数、调度方式、失败返回、费用与维护量，并在开发版真机完成一次从授权到送达的闭环。评估输出应明确：是否值得做、单用户每周能可靠提醒几次、无授权时如何显示。若平台机制不能提供稳定、低维护的体验，保留“计划时间仅排序”并把它写清楚；不要为满足报告 P0 标签而上线不可靠的提醒。

任何提醒权限状态都不能靠前端猜测“已准备”；拒绝后不反复弹窗。实际发送、定时任务、字段或环境变量变更另立 OpenSpec 和成本上限。调研预估 1 个晚上；实现工期在验证后重估。

### P1：让用户理解自己的节奏

R05、R06 优先，其次 R07 的无分享版。周总结第一版采用“最近 7 个自然日”的按需计算，不建定时任务，也不持久化报告；页面写明日期范围及计划次数。报告中的“最容易完成的时段”当前没有可靠的**实际行动时间**字段，计划时间或同步时间都不能代替它；第一版只可分析计划日的星期分布，样本不足 3 个计划日不下趋势结论。建议为透明规则，不宣称 AI 个性化推断。

助手先复用现有本机规则并入创建入口；AI 候选计划仍需独立开关、用户主动触发和确认，不能自动读取备注或创建。分享卡在周总结与隐私验收后单独实施；不做分享积分、补签奖励或转发诱导。

## 5. 开发记录与回退

每个批次单独提交到 `dev`，记录改动文件、自动测试、原生编译、真实点击、未验证项和回退提交；不混入共用云环境的其他应用资源。P0-A／P0-B 应优先保留现有数据结构，回退使用 Git revert 即可，不清理任何云端记录或本地待同步队列。提醒、分享或新字段若最终实施，先写迁移及撤回方案，再考虑部署。

建议的 OpenSpec 拆分：`improve-first-habit-and-small-goal`（P0-A）、`add-gentle-return-state`（P0-B）、`evaluate-opt-in-reminders`（调研结果明确后再决定是否进入实现）、`add-weekly-insight`（P1）。每个变更只在前一批验收后进入下一批，避免一个长期大分支使用户难以测试确认。
