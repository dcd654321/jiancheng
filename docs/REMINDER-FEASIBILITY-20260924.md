# 计划时间与订阅提醒可行性评估

日期：2026-09-24。范围：整改项 R04 的只读调研；未申请消息模板、未请求用户订阅、未创建定时触发器、未发送消息或修改云资源。

## 结论

当前版本**不开发自动习惯提醒**。保留“计划时间只用于今日排序，不发送提醒”的现有说明；不出现“已开启每日提醒”“下次提醒已准备”等未经验证的状态。

理由不是定时云函数做不到，而是普通工具类小程序可用的订阅模板与授权额度尚未在本账号核实，且一次性订阅依赖用户主动操作，不能据此承诺长期、每日送达。腾讯云官方的小程序订阅消息实操说明写明：用户主动点击授权，一次授权可发送一条服务通知；可以重复授权，但每次都需单独获得机会。[腾讯云微搭文档](https://cloud.tencent.com/document/product/1301/103770)、[腾讯云开发订阅消息示例](https://docs.cloudbase.net/recipes/add-subscribe-message-cloud-function)。从该规则推导，无重复授权就没有可承诺的每周固定提醒次数；“每天自动提醒”至少还涉及持续获取发送机会，不能仅凭设置了计划时间成立。

后续若用户测试证明外部提醒确有留存价值，只评估**用户明确点击后，为下一次计划日申请一条自愿的单次提醒**。这不是长期提醒；即使订阅接口返回同意，也必须以平台发送结果及真机收件为验收证据。微信官方开发文档入口为 [小程序订阅消息](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/subscribe-message.html)、[`wx.requestSubscribeMessage`](https://developers.weixin.qq.com/miniprogram/dev/api/open-api/subscribe-message/wx.requestSubscribeMessage.html)，本次网页读取工具无法打开微信文档页面，故不将模板类别、返回码或本账号资格写成已核实事实。

## 现状核对

- 创建页和助手页都明示计划时间仅排序、不自动提醒；“我的”说明也一致。
- 现有习惯计划保存了可选 `time` 与执行星期，今日任务排序会使用 `time`。领域模型没有订阅许可、发送次数或未来通知计划；云函数没有消息发送和定时扫描流程。
- 当前共享正式云接入、集合权限、双账户真机验收仍有独立发布门槛。本调研不改变这些状态。

## 技术与运维评估

| 环节 | 当前可依据的能力 | 本项目仍缺的验证或实现 |
| --- | --- | --- |
| 获取发送机会 | 用户主动点击后请求一次性订阅；授权不能从保存习惯或打开页面自动推断。[腾讯云微搭文档](https://cloud.tencent.com/document/product/1301/103770) | 账号对应类目是否有合适的服务通知模板、模板字段与 ID、开发版真机的同意／拒绝／不可用结果。 |
| 到时执行 | CloudBase 支持 Cron 定时触发器；需另外部署配置，时区与触发时间要在环境中核验。[CloudBase 定时触发器](https://docs.cloudbase.net/cloud-function/timer-trigger) | 独立带前缀的函数、调度粒度、跨日与用户计划变更处理；不能修改共用函数。 |
| 发送与反馈 | 云端发送需要合法模板、目标账号和未消耗的订阅机会；示例列出无授权、模板或字段不匹配等失败情况。[CloudBase 发送示例](https://docs.cloudbase.net/recipes/add-subscribe-message-cloud-function) | 可信身份绑定、同意记录、幂等防重复发送、失败后不虚报“已提醒”、取消与隐私说明。 |
| 成本 | 云函数、数据库读写和调用受云开发套餐／计费模式约束，账号实际模式须在控制台核对。[腾讯云价格文档](https://cloud.tencent.com/document/product/876/75213) | 当前 `product` 套餐、额度、账单阈值和实际调用量未核实；定时轮询还会产生空跑及数据库扫描。 |

对个人开发者，主要成本是订阅机会管理、任务变更与取消、时区、重复触发、失败重试和投诉处理，而非单次函数执行费用。若每 5 分钟轮询，单日有 288 次触发，即使无人需提醒也会运行；若每日只扫一次，又不能满足用户自选的任意计划时间。这是按 Cron 粒度推导的设计权衡，并非当前环境的实测费用。

## 若以后立项，必须先过的闸门

1. 公众平台只读核实本小程序类目、可用模板类型及字段，不以其他账号的教程代替本账号资格；记录模板的适用服务场景，不将习惯打卡包装成无关通知。
2. 在隔离测试范围设计一次性流程：用户主动点击 → 返回同意／拒绝／不可用 → 云端仅记录必要许可 → 一次发送 → 真机收件。测试不得使用现有正式用户数据。
3. 先设成本上限与停发开关；计划改变、当天已完成、暂停、归档、删除、跨日及重复触发都必须阻止不合时宜的提醒。
4. 只有上述证据齐全、且用户仍希望做时，另开 OpenSpec 变更，单独核对云函数、集合、权限、部署和回滚。拒绝授权时只保持现有排序体验，不反复弹窗。

## 验证边界

本次做了官方资料与本地代码核对，**没有**使用微信公众平台账号查模板、没有真机授权与送达实测、没有当前云环境账单核验。因此结论是“当前版本不承诺提醒，先不实现”，不是“平台绝对不支持提醒”。
