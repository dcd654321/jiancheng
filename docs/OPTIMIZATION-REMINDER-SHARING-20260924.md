# 渐成习惯打卡：多任务、提醒与分享优化方案

日期：2026-09-24　状态：产品方案，待逐项建立 OpenSpec 变更与验证

落地文档：[功能详细设计](FEATURE-DESIGN-20260924.md) · [增量数据库设计](FEATURE-DATABASE-20260924.md)

## 1. 结论与边界

产品继续聚焦个人反复要做的小事，核心体验是「再忙也能做一点，断了也能回来」。本轮新增的分享要让接收者**看见一份有用的计划或真实进展**，而不是只收到空泛的小程序入口。多个任务以「今天先做哪件、怎样快速记下」为中心，不扩成待办、日历或社群产品。

本方案只新增文档，不代表功能已实现、云端已部署或微信平台审核已通过。所有代码、集合、正式环境与发布动作另行执行；继续只在 `dev` 开发，用户验收并明确要求后才考虑合并 `main`。

### 已有与待做

| 能力 | 当前代码 | 本方案 |
| --- | --- | --- |
| 多习惯 | 最多同时活动 5 个；今日待完成在前，已完成可折叠；每项可打卡或先调小目标 | 提升 3—5 项并用时的扫读、排序和快捷动作，不先提高上限 |
| 提醒 | 计划时间仅用于排序；无通知发送 | 自愿申请「下一次聚合提醒」，平台条件不成立时如实降级 |
| 分享 | 业务页面无好友／朋友圈分享；现有 `wx.shareFileMessage` 仅用于备份文件 | 小程序邀请、可阅读的计划／进展快照、朋友圈适配、本人分享列表 |
| 意见反馈 | 「我的」已有微信原生 `open-type="feedback"` 的「问题反馈」按钮 | 改为更易发现的「意见与问题反馈」，真机核验入口；首版不自建工单系统 |
| 云端 | 旧测试环境仍是活动配置，共享正式环境配置关闭 | 新公开分享与提醒不得绕过正式云身份、权限和双用户验证 |

## 2. 多个打卡任务：今日页优先做好

用户有 3—5 个习惯时，最重要的不是展示更多卡片，而是让每次打开都能在几秒内找到下一项。

1. 顶部显示「今天待做 3 项／已完成 2 项」，数值只统计今天安排的习惯；休息日不算未完成。
2. 待完成列表默认按**用户手动置顶（最多 1 项）→ 今天的计划时间 → 无时间**排序。计划时间只表示用户想做的时段，不等于已开启通知；不做动态跳动排序，避免列表在操作时换位。
3. 每项保留清晰的习惯名、平时／忙时目标和一个主按钮「完成打卡」。已有忙时目标时另给「按忙时目标打卡」快捷动作；它必须明确表示用户**已经做完**该动作，不能把「调小目标」误当「完成」。没有预设忙时目标则维持现有输入、确认流程。
4. 完成后任务移入折叠的「已完成」区，原位置短暂显示可撤销提示；待同步时显示「待同步」，绝不把本机乐观状态当云端已确认。
5. 全部完成时只给简短反馈和明日安排，不制造新的任务。保留「添加习惯」入口，但已有 5 个活动习惯时说明上限及暂停／归档办法。
6. 不提供「全部一键完成」：打卡是用户声明已实际执行，批量打卡会降低记录可信度。

**页面结构**：今日页仍是「概览 → 待完成卡片 → 已完成折叠 → 添加习惯」。首次使用及断档回归引导仅占一处，不能把 3—5 项真实任务挤出首屏。进度页增加「按习惯看」入口，但不增加底部 Tab。

**验收**：在 320px 宽、系统大字号和 Android/iOS 真机上，以 0、1、3、5 项以及跨日／离线待同步状态走查；每个任务的打卡、忙时打卡、撤销不得误操作到相邻任务，标签与读屏文字能区分「原目标完成」和「忙时目标完成」。

## 3. 提醒：多任务只发一条聚合消息

### 用户流程

「我的 → 提醒」显示：计划时间、下一次可提醒的日期、通知状态。用户可选一个统一提醒时刻，例如 20:30；当日尚未完成的多个习惯合并为一条「今天还有 2 件小事」，点开进入今日页，不按习惯逐条轰炸。首次完成一次打卡后再轻提示该入口；拒绝后不反复弹窗。

用户点击「提醒我下一次」才调用订阅授权。授权成功也仅表示**取得一次发送机会**，页面须区分「已申请，待平台发送」「已发送」「未授权／被拒绝」「未发送／失效」；没有可靠送达证据时，不写「每日提醒已开启」。若当天任务都已完成、计划被暂停或删除，则取消待发，不浪费通知打扰用户。

腾讯云关于微信小程序订阅消息的[实操文档](https://docs.cloudbase.net/recipes/add-subscribe-message-cloud-function)说明：一次性订阅通常每授权一次只可发送一条。能否申请到**与个人习惯提醒真实场景相符**的模板、当前小程序主体和类目能否使用、共享云环境如何发送，都必须先在本账号后台与真机核实。因此「长期自动每日提醒」不是本方案的已承诺能力；若无法合规、稳定实现，保留计划时间排序及产品内提示，不显示假的提醒开关。旧[提醒可行性评估](REMINDER-FEASIBILITY-20260924.md)仍作为实施闸门。

### 服务端安全与成本

- 待发记录仅存本项目带前缀的资源，例如 `jiancheng_daka_reminders`；可信账号来自平台上下文，不接受客户端传来的 OpenID 作为目标身份。
- 一条待发记录与一次订阅机会关联，发送前再次检查日期、习惯状态、是否全部完成、用户取消和授权是否已消费；以幂等键防重复。
- 失败或发送结果未知时不伪报成功。设置全局发送上限、异常停发开关、清理到期记录；先测实际调用费用，再定扫描频率。不为 5 个任务运行 5 套定时扫描。
- 真机验收覆盖同意、拒绝、已授权但取消、重复触发、跨日、已完成不提醒、收到消息后进入正确页面。平台只支持单次机会时，文案始终写「下一次提醒」。

## 4. 分享：让接收者真的有内容可看

这里将「分享内容」首版限定为两类，避免引入书籍、冷知识等内容运营：

| 类型 | 发起者预览 | 接收者可见 | 接收者价值 |
| --- | --- | --- | --- |
| 轻计划 | 从阅读／步行／复习／整理等预设类别选择公开标题，加上平时目标、忙时目标；自选是否显示执行星期 | 同一份只读计划，不显示发起者的私有记录 | 可参考并「创建同款」，保存到自己的账号前仍可修改 |
| 一周进展 | 行动次数、原目标／忙时目标次数及一条预设感受文案 | 发布当时的只读快照 | 看见具体变化，理解小目标玩法 |

另有「分享小程序」邀请卡：说明「平时做一点，忙时做更少」，接收者打开后可直接选阅读／走路／复习等模板。邀请卡不附带任何习惯或账户数据；从「分享」页创建邀请卡时也进入「我的分享」列表。

首版不公开用户自填的习惯名、备注、感受或上传图片，也不提供自由编辑分享文案。自定义内容若以后开放，必须另做内容安全审核、举报／下架和运维预算，不能直接把现有私人备注复制到公共页面。

### 发送和接收流程

1. 发起者在习惯详情、周进展或「我的 → 分享」选择类型，**先看到最终公开内容预览**。默认不含昵称、私人习惯名、备注、具体打卡日期、私人时间和其他习惯；公开标题只从预设类别中选择。
2. 点击「创建分享」后，服务端保存不可猜测 ID 对应的**脱敏快照**，返回可访问的分享详情页；快照创建成功才出现「发给微信好友」按钮。不要在 `onShareAppMessage` 同步回调里临时创建数据库记录。
3. 微信好友／群打开卡片进入只读详情页；未同意保存个人数据的接收者也应能看完整分享内容。想「创建同款」时才进入自己的首次使用／创建流程，不会接触原作者账户。
4. 朋友圈只能由用户从**当前可分享页面**的微信菜单发起，程序不能替用户自动发布；详情页需实现 `onShareTimeline`，保证朋友圈单页模式下内容本身可读，不依赖登录、跳转或 TabBar 才显示核心信息。若账号、客户端或共享云的访客读取能力无法满足，就不能宣称朋友圈小程序卡片已可用；可另提供用户自行保存、手动发朋友圈的图片，但图片不是可点击的小程序详情页。[微信朋友圈能力说明](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/share-timeline.html)；[腾讯云带参分享示例](https://docs.cloudbase.net/recipes/add-share-with-params-miniprogram)。

### 「我的分享」及隐私

「我的 → 我的分享」列出本人**创建的分享内容**，按时间倒序，显示类型、标题、创建日和「可查看／已到期／已撤回」状态；可预览、再次分享、撤回公开访问。默认公开有效期 90 天，到期后外部访问显示「这份分享已失效」；本人可删除历史条目。删除个人数据时一并撤回并清理本人分享快照。

微信分享动作无法作为可核验的「已发送给某人」「对方已收到」事实。因此页面标题可以叫「我的分享」，但说明必须写「这里记录你创建的分享，不记录发给了谁」；直接通过系统菜单转发、没有先创建公开卡片的行为也不列入此列表。不提供虚假的已送达、朋友圈曝光或联系人列表。若未来做打开次数，仅统计匿名、去重的粗粒度数据并在隐私说明中告知，不用它发放奖励。**不做分享积分**，避免为无法核实的动作发奖及诱导传播。

### 公共快照的服务端边界

- 新集合只用 `jiancheng_daka_` 前缀，例如 `jiancheng_daka_shares`；客户端不可直接枚举或写集合。创建／撤回／本人列表必须鉴权，公共读取只返回经过白名单过滤的快照，不读取私人账户原文。
- 分享 ID 由服务端生成足够长的随机值；默认最多保留 50 个有效分享／人，限制创建频率、公共查询频率和单份内容大小；到期及撤回立即停止公开读取。
- 朋友圈单页模式可能没有普通登录态，且当前是共享正式云环境。要先在隔离测试中证明访客**仅能读取这份公开快照**；绝不可为打通分享而开放 `jiancheng_daka_accounts` 或其他小程序集合。无法满足时先不发布该分享入口，不能用前端页面遮挡来假装隔离。
- 接收者在别人的分享页只看到公开快照；两个不同微信用户互相测试，验证不能通过改 ID 或请求参数读到对方私人数据。

## 5. 意见反馈

现有「我的 → 问题反馈」使用微信原生反馈入口，先保留并改名为「意见与问题反馈」，在「使用帮助」里补一句「可提交建议或报告故障」。首版不建自有反馈数据库，不索取手机号，不让用户重复填账号信息。真机验证入口是否可用、开发者后台能否收到反馈；如需站内处理状态／回复，再单独立项自建反馈单与隐私、反滥用设计。原生反馈不应宣传成「我的反馈记录」。

## 6. 交付顺序、成本和验收

| 批次 | 范围 | 个人开发的预估 | 发布门槛 |
| --- | --- | --- | --- |
| A 基础可靠性 | 正式云身份／权限、双用户与弱网验收；多任务今日页；反馈入口真机核验 | 多任务约 2—3 个晚上；正式云耗时取决于权限问题 | 不能读错账号、丢打卡或误报云端已保存 |
| B 分享 | 小程序邀请、轻计划与周进展快照、好友／朋友圈、我的分享与撤回 | 约 5—8 个晚上，访客权限可能增加工期 | 接收者真机可读；单页模式可读；撤回后不可读；无隐私外泄 |
| C 提醒 | 本账号模板核验、一次性聚合提醒、取消／失败状态与限流 | 可行性核验约 1 晚；若可用，实现约 3—6 晚 | 用户主动授权、真机实际收到、无重复与误导文案 |

这些是粗估，不含微信审核等待或云环境异常处理。每批先写 OpenSpec 提案与测试，再实现、跑 `npm test`／`npm run check`／`npm run check:cloud`／严格规范校验，随后原生编译与真机走查；每批独立提交 `dev`，记录回滚提交。新云集合或定时器部署前单独列出确切资源和恢复方案，不触碰共用环境中其他应用。当前未修改业务代码、未部署、未提交。

**成功判据**：5 名非开发者能独立完成「建 3 个习惯 → 分别普通／忙时打卡 → 查看我的分享 → 撤回 → 提交意见反馈」；提醒在获得本账号可用模板后另用真实微信测试。观察首日完成率、7 日重复打卡和分享接收者「查看／创建同款」转化，不把分享按钮点击数当成发送成功数。

## 7. 实施前必须核实的两处平台条件

1. 当前个人主体小程序是否有与习惯场景相符的订阅消息模板，以及真实一次性授权和发送行为；若没有，批次 C 改为仅产品内提醒，不承诺后台推送。
2. 朋友圈单页模式在本小程序与共享云环境中能否安全读取公开快照；若不能，批次 B 的朋友圈先交付手动保存图片方案，但好友可打开的内容页仍须满足只读、安全与撤回要求。

这两项属于技术／平台闸门，不应由文案或模拟测试代替。
