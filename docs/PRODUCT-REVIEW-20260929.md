# 产品评审与优化方案（2026-09-29）

> 评审方式：不看设计文档，直接通读小程序全部页面代码（13 个页面、共享模板、服务层、领域规则，约 3000 行），以挑剔产品经理视角评审易用性、美观性、信息架构与核心循环。
> 视觉判断基于 WXML/WXSS 实现推导；交互与文案判断基于代码逻辑，均标注了代码出处。

---

## 一、总评

**「工程品味很好、产品手感欠佳。」**

文案的温度感、边界情况的处理（6 秒撤销、温和回归、5 个习惯上限）明显高出同类产品，但存在三个硬伤：

1. **核心动作的情绪回报是平的**——打卡完成后用户得到的反馈是一句「已保存到云端」；
2. **断网即瘫痪的云端策略对打卡产品是致命伤**——地铁、飞机等弱网场景正是打卡的高频时刻；
3. **视觉层几乎没有设计**——全站是白底列表加 1px 分隔线，缺少「每天想打开」的产品质感。

它现在像一个精心打磨的后端，配了一个 MVP 的壳。

## 三、问题与优化方案

### P0-1 断网完全瘫痪 + 每次冷启动白屏等待

**现象与证据**

- [cloud-session.js:13](../miniprogram/services/cloud-session.js:13) 明确注释：`No device storage or offline queue`。
- 断网时所有页面整页显示「暂时无法读取云端记录」，打卡被拒（`当前无网络，云端保存不可用`）。
- 每次冷启动，页面先渲染「正在读取云端记录，请稍候」，网络慢几秒用户就看几秒 loading。

**影响**：习惯记录的使用场景（碎片时间、通勤、弱网）与架构直接冲突。这是产品级否定，不是体验瑕疵。

**优化方案**

1. **最低限度（建议立即做）**：云端快照成功拉取后写入微信本地存储；冷启动先渲染缓存数据并标注「上次同步时间」，后台静默刷新。可消灭启动白屏，成本极低，不涉及写冲突。
2. **进阶**：打卡操作离线入队，联网后重放，列表项标注「待同步」角标。写入已具备 `operationId` 幂等键（[cloud-session.js:191-204](../miniprogram/services/cloud-session.js:191)），重放的技术地基已铺好一半；领域层 `validateState` 足够严格可兜底冲突（冲突时降级为只读提示）。
3. **若坚持纯云端**：至少把「断网」从整页 error 降级为顶部一条状态横幅 + 允许只读浏览。

### P0-2 核心动作（打卡）完成后情绪回报约等于零

**现象与证据**

- 完成打卡的反馈是 `icon: 'none'` 的 toast「已保存到云端」（[ui.js:44-49](../miniprogram/services/ui.js:44)）；首次打卡是「第一步已保存到云端」。
- 当日全部完成只是列表悄然变空，没有任何完成时刻。
- 反馈对象是「云端存储确认」，不是「用户的努力」。

**优化方案**

1. toast 改为「✓ 已记录」，配 `wx.vibrateShort` 轻震动 + 打卡按钮 200ms 填充动效。
2. 当日全部完成时给一个明确的完成时刻：一行祝贺 + 当期完成数据收尾卡片。不引入连续打卡天数（违背产品反焦虑哲学）。
3. 文案原则：所有操作反馈对用户说「你做了什么」，对系统说「数据怎样」；后者放次级位置或省略。

### P1-1 备注是「只写不读」的

**现象与证据**

- 备注存储在每天的 record（[habits.js:124-127](../miniprogram/core/habits.js:124)），但详情页只展示**今天**的备注（[detail/index.js:50](../miniprogram/pages/detail/index.js:50)）。
- 进度页历史列表只显示状态和目标，不显示备注。
- 用户坚持写一个月，回看入口为零。

**优化方案**

1. 详情页增加「备注回顾」入口：按日期倒序列出非空备注（近 28 天起，后续可扩展全部）。
2. 进度页选中某天的记录列表中，当日备注直接展示一行摘要。

### P1-2 新用户创建第一个习惯的漏斗太长、文案不闭环

**现象与证据**

- 空状态 4 个模板 chip「读5分钟」「走路10分钟」点击后**仍要填完整个表单**（5 个字段）。
- chip 写「读5分钟」，预填标题却是「读一会儿」（[edit/index.js:3-8](../miniprogram/pages/edit/index.js:3)），用户会怀疑点错。
- 对主张「从一件小事开始」的产品，首次创建应是全站最顺滑的路径。

**优化方案**

1. 首次使用时模板 chip 点击**直接创建默认计划**（名称/目标/每天全预填），toast「已创建，可随时调整」后回今日页打卡——两步完成；想改的人进详情或表单。
2. 老（多习惯）用户维持完整表单。
3. 统一 chip 文案与预填标题（chip 显示什么，表单就预填什么）。

### P1-3 同一概念有四个名字

**现象与证据**

| 出现位置 | 用词 |
|---|---|
| edit 表单 | 忙时的小目标 |
| 今日页快捷按钮 | 按忙时目标打卡 |
| 今日页/详情完成态 | 小目标完成 |
| 领域层 statusText | 简化完成（[habits.js:48](../miniprogram/core/habits.js:48)） |
| 进度页图例 | 部分完成 |

**影响**：用户无法建立「这几个词说的是一回事」的认知，帮助文案也不得不反复解释。

**优化方案**

1. 全站统一为「**小目标**」一个词（含领域层 statusText 同步改）。
2. 进度页图例的「部分完成」与任务级「小目标完成」颗粒度不同，图例改为「有完成」/「有记录」并补一句解释。
3. 建立一份约 10 行的文案词汇表（术语、语气、禁用词），新文案评审对照。

### P1-4 今日页引导横幅堆成「告示板」

**现象与证据**

- 断网/同步提醒条 + 首次创建引导 + 回归引导 + 短句，极端情况同屏 3-4 个提示块叠放，且样式同为 `.notice`（[today/index.wxml:8-17](../miniprogram/pages/today/index.wxml)），用户不知道先看哪个。

**优化方案**

1. 定优先级规则：**状态类（同步/断网）合并为顶部一条细横幅；引导类（首次/回归）同屏最多一条**。
2. 短句在存在任何引导时隐藏（回归引导已做，规则应全局化）。

### P1-5 AI 助手页被合规文案淹没、漏斗多一跳

**现象与证据**

- 一页三段免责：「不发送给AI」「DeepSeek 仅接收方向和可用分钟……不保证效果」「不承诺固定天数养成习惯，不提供医疗或训练处方」（[assistant/index.wxml](../miniprogram/pages/assistant/index.wxml)）。诚实是对的，但三段堆在决策点周围，页面气质从「温柔助手」变成「法务文档」。
- 流程：基础建议 → 预览 →「使用这个计划」→ 又进编辑表单，共 2 页 + 1 预览 + 1 表单才创建一个习惯。

**优化方案**

1. 三段合规合并为一段可展开的「数据与效果说明」，默认收起。
2. 基础建议预览卡片直接放「确认创建」；AI 细化作为可选项。
3. 预览卡与编辑表单数据完全一致时，砍掉中间一跳（预览 → 直接进表单仅当用户要改）。

### P2-1 视觉层没有体系，缺「被设计过」的证据

**现象与证据**

- 全站白底 + 1px 分隔线列表，唯一强调色 `#245c44`，唯一的卡片容器在分享预览页。
- 完成态只是文字变灰（[app.wxss:40](../miniprogram/app.wxss:40)），无插画/图标语言（仅原生 circle/success 图标），进度条是 8px 素条。

**优化方案**（不必推翻极简风格，注入三点即可）

1. 任务卡片化：8-12px 圆角 + 浅底；完成态用绿色勾 + 淡绿底，替代灰字。
2. 打卡按钮填充动效（与 P0-2 一并做）。
3. 进度页 28 天日历格子只保留日期 + 色块，「2/3」明细移到点选后的下方列表——信息已存在，纯减负；小屏上三行文字塞约 43px 宽的格子已经拥挤（[progress/index.wxml:15](../miniprogram/pages/progress/index.wxml:15)）。

### P2-2 进度页只有数字，没有洞察

**优化方案**

- 加一条本地自动生成的洞察文案，放在分段器下方：「你完成率最高的习惯是 XX」「本周比上周多记录 N 次」。纯本地计算，不需要 AI，却能显著提升打开进度页的理由。

## 五、落地建议的顺序

1. **第一批（1 次发版内）**：P0-1 本地快照缓存（先只做「可看」）、P0-2 打卡反馈。两者改动面小、收益最大。
2. **第二批**：P1-1 备注回看、P1-2 首建漏斗、P1-3 术语统一（一次发版集中改词，避免分期造成新旧混用）。
3. **第三批**：P1-4 / P1-5 / P2 逐项排入。

> 每批发版前跑一遍既有回归（tests/），术语变更需同步检查帮助文案与隐私说明中的用词。
