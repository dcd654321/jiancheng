# Design

## Context

动机见 `proposal.md`；行为契约见 `specs/habit-deletion/spec.md`。提案建立时已核验的实施前本地源码：

- `miniprogram/pages/detail/index.wxml` 的更多操作只绑定 `onStatus`；`index.js` 用习惯 revision、账户 context 和页面访问版本保护状态确认。
- `miniprogram/core/habits.js` 的纯 reducer 未提供删除；记录以 `id@date` 存放，状态校验禁止记录引用不存在的习惯。
- `server/protocol.js` 维护命令字段白名单；`server/handler.js` 以受信身份执行账户事务，检查 operationId、epoch、expectedRevision、操作日期，保存回执。
- `server/cloudbase-repository.js` 在账户事务中持久化账户与回执；偏好位于 `jiancheng_daka_preferences`。现有全账户 purge 会更换 epoch 并清理旁路资源。
- `cloud-session.js` 会在内存预校验命令，但只接受合法云快照；结果未知保留原请求供重试。`ui.mutate` 共享写入锁和页面有效性判断。
- `server/features.js` 保存公开分享独立快照，只依据账户 epoch 判断整账户删除后的失效；分享没有可用于精确关联历史习惯的持久源标识。`reminder-worker.js` 发送前再次读取账户并重算待做数量。

这些是实施前源码观察，不代表线上已经部署或真实账户验证。实施结果见 `docs/HABIT-DELETION-20261010.md`。

## Goals / Non-Goals

**Goals:**

- 用现有 mutate 协议增加小范围单项删除，保持数据格式与旧客户端兼容。
- 将目标习惯、记录和命中的置顶引用一并提交；保留操作回执以核对未知结果。
- 将确认对象、数据版本、日期和页面访问绑定，明确失败与成功后的页面行为。

**Non-Goals:**

- 不增加本机持久数据、离线删除队列、回收站或自动恢复机制。
- 不更换账户 epoch，不复用全账户 purge，不增加集合、索引或权限。
- 不扫描和删除全部分享、偏好、提醒或共用资源；公开分享与提醒沿用已说明的边界。

## Decisions

### 1. 使用 deleteHabit 命令

新增 `{ type: 'deleteHabit', id, baseRevision }`，接入既有 `action: 'mutate'`。白名单拒绝其他字段，id 和 baseRevision 与计划修改使用相同的格式校验。删除不是记录补报类命令，沿用 handler 的当天确认要求。

纯 reducer 先查找目标并匹配 habit.revision，随后从 `habits` 删除目标、按记录自身 `id` 精确移除目标的全部记录，增加 state.revision 并保持其他内容原值。事务和客户端预校验均验证结果状态。目标不存在时明确拒绝；同一 operationId 的成功重放由云回执处理，不把任意缺失目标当作成功。

选择此方式是因为现有协议已提供账户隔离、容量检查、冲突和幂等。另开删除 API 会重复这些机制；归档仍保留历史，不能满足删除契约；整账户 purge 的清理范围过大。

### 2. 删除与置顶引用清理保持原子性

`createRepository` 在提交账户前，比较同一 epoch 的前后习惯标识，识别此次单项移除。在同一数据库事务内读取该 owner 的偏好文档；缺失偏好无需创建。复用或提取现有偏好校验，确保 owner、ownerEpoch 和格式可信。仅当 `pinnedHabitId` 命中目标时设为 null、递增偏好 revision、更新 updatedAt，其他字段逐项保留。

任一读写、权限或格式错误都使事务回滚；不能账户先成功、偏好后失败再宣告完整成功。全账户 purge 继续使用现有 epoch 清理流程，不触发此单项路径。偏好同时被其他设备写入时，数据库事务冲突重试与偏好 revision 继续提供保护。

成功返回“我的习惯”后按已确认账户重新投影清单；今日重新出现时按原流程读取偏好，客户端旧缓存即使短暂保留旧标识，也不生成已不存在习惯的任务。测试需要证明原子提交、回滚、偏好缺失、不同置顶及同 epoch 限定。分两次调用“先取消置顶再删除”会产生部分成功，故不采用。

### 3. 确认与提交绑定原对象

详情新增 `onDeleteHabit` 和确认锁；入口禁用条件包含数据只读、写入中、置顶中及确认处理中。无效详情不展示入口。弹窗使用现有危险色 token，文案见提案，不把暂停/归档的“明日生效”说明套用到删除。

打开确认前断言当前 context 和可写状态，捕获 id、title、habit revision、已确认 state revision、业务日期、context、showVersion。确认回调检查页面仍有效、日期未变、当前已确认状态 revision 与捕获值一致、目标仍存在且 revision 一致，再用捕获参数提交。其他设备在提交后抢先修改则由云端 expectedRevision 拒绝。确认锁在取消、失败和完成时释放；重复回调不能创建第二个请求。

保留共享 `ui.mutate` 的串行锁和云会话的原请求重试机制，按需增加删除的“正在删除…”及“正在确认删除，请稍候。”文案，不改变其他命令的状态文本。

### 4. 成功、失败和迟到回执

不提前修改习惯列表或清除草稿。合法回执确认后，只移除原 context 下该 habit 的备注草稿；如果状态来自后续原请求重试，则在成功核对后也执行清理。拒绝、未知结果或服务错误保留草稿和当前错误/读取出口。

导航与 toast 仅允许原 context、showVersion 且当前可见的详情执行，失败不导航，迟到回执不操作新访问。成功返回“我的习惯”并提示“习惯已删除”：页面栈中已有管理页时退回，否则替换详情进入管理页；导航失败显示“返回我的习惯”出口。共享 mutate 会刷新页面，需保证刷新为无效详情不阻断成功处理，且不重复提示。

云会话在回执验证完成后触发 `subscribeConfirmed`，包括原操作重试的成功回执。工作区按回执账户和 epoch 清理目标草稿，详情按原命令、账户和页面访问标记确认后导航；拒绝或无效回执不触发。详情同步读取合法快照发现目标已移除时，也清理该 context 的目标草稿。使用真实 store/session 测试这些路径，避免夹具遗漏 contextKey 导致误判。

### 5. 关联功能与统计

- 今日、详情历史和进度均从账户状态投影；删掉习惯与记录后自然排除目标，不维护额外本机统计。
- 既有公开分享是已发布快照，单项删除不自动撤销，确认弹窗明确提示用户使用分享管理。新分享预览使用新状态，旧预览的 sourceRevision 在云端创建时被拒绝。无需修改分享文档格式或追溯迁移。
- 提醒面向账户某日待做数量，保留现有发送前二次核对。删除先于最终核对时目标不计入；已进入微信发送过程的消息沿用“在途消息不可撤回”边界，不承诺撤回。

## Risks / Trade-offs

- [不可恢复删除] → 在提交前展示目标与全部记录范围；取消无写入，不提供误导性的撤销。
- [删除与偏好写入不同步] → 同一事务提交，偏好权限不足时整个删除失败并保留数据。
- [回执丢失] → 保留相同 operationId 重试，成功回执与合法快照才更新展示，不创建持久离线队列。
- [已有分享仍含删除前的公开内容] → 确认提示单独撤销，保留现有分享管理入口。
- [本地包含大量其他未提交改动] → 仅修改本变更相关文件，逐项审阅差异，不覆盖、提交或部署整批用户工作。

## Migration Plan

1. 用户审阅提案并授权实施后，在 dev 完成源码和回归，运行 `npm run build:cloud` 生成云模块，检查差异。
2. 自动验证分别执行 `npm test`、`npm run check`、`npm run check:cloud` 与 `npm run openspec -- validate --all --strict`；SDK 合同测试先确认业务云函数锁定依赖可用。
3. 部署单独授权后先更新测试环境 `jiancheng_daka_api`，再测试客户端。目标仅为渐成账户和偏好集合，权限沿用现有受信身份范围；不迁移、扫描删除或恢复已有数据。其余云函数是否需同步公共生成模块，以构建差异和实际部署依赖核验后精确列出。
4. 真机、双账户与双设备冲突验证使用明确授权的专用测试习惯，逐次说明删除目标、记录范围和不可恢复边界。未获真实删除授权只执行模拟和只读验证。
5. 回滚先关闭或撤回客户端删除入口，再回退本次云代码。旧客户端继续支持剩余状态；代码回滚不能恢复已删除习惯、记录或草稿，不从旧快照自动回灌。
6. 用户验收后另行处理归档、提交或合并发布，当前不执行这些动作。
