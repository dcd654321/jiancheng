# Design

## Context

动机和验收目标见 proposal.md。当前 `cloud.js` 指向旧测试环境的 `habitApi`；预备 product 配置关闭且无环境 ID。传输层只调用默认 wx.cloud，未提供资源方信息。服务端只验证 APPID/OPENID/SOURCE，账户键由小程序与用户身份共同派生；现有事务、幂等回执和队列不能被接入改动破坏。

历史检查定位 product 环境为 `product-d2g59zty74d7d1ec1`，资源方为 `wx7ad85943fe81e095`，使用方为 `wx58e61dffcbfa4249`。这些非密钥标识仅为实施前复核线索，本轮不查询或修改云资源。已有测试覆盖命名、失败不回退、缓存隔离，但没有跨应用真实身份验收。

## Goals / Non-Goals

**Goals:** 增加显式的共享访问模式与可信来源适配，保持现有业务协议、幂等和独立存储语义；客户端切换与云端准备分别验收。

**Non-Goals:** 不自动合并测试和正式数据，不统一其他应用的认证，不改变习惯规则、AI或页面布局，不删除旧资源，不实施本提案。

## Decisions

1. 传输层按明确配置选择默认或共享模式。共享模式创建带资源方与环境标识的独立 Cloud 实例并等待初始化；用单一初始化 Promise 合并并发，失败后允许显式重试。保留旧模式用于受控测试，禁止失败时自动回退。直接替换默认全局环境无法表达资源归属，因此不采用。
2. 将可信上下文的来源身份适配放在服务端边界，再交给现有账户处理逻辑。共享来源字段的确切语义依据当前官方 SDK 文档及授权测试调用核验；只有受信来源完整且匹配使用方白名单时才标准化，不把资源方身份误认成用户来源，不从 event 补全身份。无法证明身份映射时停止上线，不以放宽校验作为备选。
3. 继续使用 `jiancheng_daka_accounts` 及正式独立存储命名空间。切换时旧队列留在原范围，不重放到正式环境。保留 epoch、revision 和 operationId 处理，不迁移业务数据结构。
4. 正式函数独立配置现有 HABIT_* 开关，核验禁止客户端直读写业务集合及实际来源限制。数据库权限和函数配置变更需执行前授权。只读核验共用 cloudbase_auth；若必须修改，则暂停本次实施，另行列出跨应用影响，不能夹带修改。
5. 本地源码和远端部署分别记录版本与证据；不要把 OpenSpec 文件存在性校验或单元测试当作云端验收。双账户、真机及用户验收是独立检查项。

## Risks / Trade-offs

- [共享身份语义判断错误] → 查官方资料并使用受控身份验证；只保留脱敏结果，不记录原始 OpenID。
- [旧队列跨环境写入] → 覆盖旧缓存、新账户、失败恢复和冲突回归测试，保持存储范围隔离。
- [远端配置已有变化] → 部署前实时核对目标、代码、变量和安全规则，并保存可恢复的变更前配置。
- [共用认证配置不兼容] → 不自动修改共用函数，停止并请求扩展授权。
- [已经产生正式数据后回退旧测试环境] → 保持正式缓存和数据原位，使用停止写入或修复正式服务的策略，不静默切回旧账户。

## Migration Plan

1. 在 dev 完成新增测试、共享传输及可信身份适配，验证本地构建副本一致性；此阶段不切换活动环境。
2. 取得远端操作授权后，复核资源归属、共享关系和本项目配置，保存代码及配置快照，再只部署本项目新函数。
3. 通过受控调用、权限隔离和持久化验证后，再在 dev 切换活动目标，并使用独立缓存范围。
4. 用户按 tasks.md 进行真机验收。只有用户明确要求才合并 main；本提案不授予发布权限。
5. 回滚使用对应提交的 Git revert 与经核验的本项目云端代码/配置快照。已产生正式数据时不删除集合、不搬迁队列、不隐式切回测试环境；故障期间停止新写入并保留恢复证据。

## Open Questions

实施前需重新确认远端当前部署版本、变量与规则是否与历史记录一致，以及可用于双用户验收的测试账号。这些属于执行前置条件，不改变“不放宽身份、不改共用资源、不迁移数据”的方案；无法满足时暂停对应任务，不猜测通过。

## Authorized staged deployment (2026-09-27)

用户在明确说明 product 专属资源部署授权边界后回复“继续吧”，允许本应用部署推进，不包括其他应用、共用认证、main 合并或发布。当前工具只有名称/状态/运行时/超时元信息，无法导出旧主函数代码及配置，因此主函数覆盖仍停止。

在完整身份验证前，只允许独立创建已确认远端不存在的四个新函数，并保持所有服务端能力门禁及客户端入口关闭。不设置启用变量、定时器、模板或供应商密钥；不改集合权限或写入业务记录。部署前确认锁定依赖、构建一致和缺配置时在业务读取/发送之前拒绝。这个阶段只验证包部署和关闭状态，不完成 1.2、1.3、3.1 或正式启用验收。

原函数不存在的清单是创建基线；保留本地源码提交和部署结果，不覆盖旧主服务。新函数若部署失败/状态不明，不自动重建或删除；若需回退，先保持未启用，删除需另行说明精确资源。正式启用仍依赖备份、可信身份、安全规则和实际联调。

## Resolved initialization errors (2026-09-27)

独立的本应用 AppID 诊断页面在基础库 3.17.3 下确认：共享 `init()` 返回的 Promise 会 resolve 一个 `{errCode:403, errMsg:...}`，其提示为当前小程序未获资源方云环境共享权限。随后调用业务函数才出现笼统的“未初始化”。因此 Promise resolve 不能单独作为成功判据。

传输层在取得 init 返回值后，如返回对象显式含 errCode，则仅数值 0 允许继续；非零或格式异常的码视为初始化失败。数值 403 映射为固定的“正式云共享权限尚未开通，请联系开发者处理”，其他失败码使用固定初始化失败提示，不将原始 errMsg、auth 或身份资料写入用户状态。继续兼容 SDK 不返回值的成功形式；失败后清空 initPromise，并发等待者共同失败，下一次显式请求允许重新初始化。

该修复只改善本应用的失败处理，不改变服务端身份策略或共享授权。拒绝发生在业务调用前；仍需核对资源方的共享设置及共用认证，涉及共用配置修改时须单独授权。

用户进一步要求整理所有集合/函数并在正式环境创建。已对照源码汇总五个函数、七个集合、四个业务索引以及提醒 Date TTL 要求，见 `deploy/product-resources.json` 与 `docs/PRODUCT-RESOURCE-INVENTORY-20260927.md`；该清单归并既有分享/提醒/AI/限额提案所需资源，不新增产品行为。

本轮完整 listCollections 返回六个其他应用集合而无本应用集合，与此前 checkCollection=true 相矛盾。以完整清单为准创建缺失空集合，创建后再次用完整列表及可验证索引明细确认；不把响应成功提示当资源已存在。现有五个函数不重复创建，代码版本未知的函数先核验再决定更新。普通索引按明确缺失项添加，不全量重放可能删除重建同名索引的请求；TTL 参数未核实前不伪装成普通索引完成。七集合都要求客户端禁止直接读写，权限未核验前不写业务数据。
